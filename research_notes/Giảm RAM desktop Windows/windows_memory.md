# Windows desktop memory accounting and the 2–3 MB total working-set target

Research date: 2026-10-29. Scope: Windows 11 x64; documentation research and review of existing measurements only. No application changes, trimming experiments, settings changes, or UI operations were performed. “MB” needs an explicit definition in acceptance tests: 3,000,000 bytes differs from 3 MiB = 3,145,728 bytes.

## What exactly does total working set measure?

### Takeaway

Keep total working set as the requested headline metric. Private resident memory and committed private memory answer different questions and must be reported separately; neither can establish compliance with a total-working-set cap. [Microsoft: WorkingSet64](https://learn.microsoft.com/en-us/dotnet/api/system.diagnostics.process.workingset64?view=netframework-4.7.2); [Microsoft: PROCESS_MEMORY_COUNTERS_EX2](https://learn.microsoft.com/en-us/windows/win32/api/psapi/ns-psapi-process_memory_counters_ex2)

### Cited Findings

- `WorkingSetSize` is current resident working-set bytes; `PeakWorkingSetSize` is its lifetime peak. `PrivateWorkingSetSize` is private resident bytes. `PrivateUsage` and `PagefileUsage` are private committed bytes, not a measurement of bytes currently on disk. These fields are separately defined in `PROCESS_MEMORY_COUNTERS_EX2`, supported by the documented recent Windows 10/11 updates. [Microsoft: PROCESS_MEMORY_COUNTERS_EX2](https://learn.microsoft.com/en-us/windows/win32/api/psapi/ns-psapi-process_memory_counters_ex2)
- The working set includes shared and private resident pages, including instructions in application modules and system libraries. `.NET Process.WorkingSet64` corresponds to the process Working Set performance counter; call `Refresh()` before obtaining an up-to-date value through that API. [Microsoft: WorkingSet64](https://learn.microsoft.com/en-us/dotnet/api/system.diagnostics.process.workingset64?view=netframework-4.7.2)
- Microsoft defines private working set as recently referenced private, non-shareable pages, while process working set includes private and shared pages. Shareable executable-image pages include DLL and EXE code. [Microsoft: Memory Footprint Optimization](https://learn.microsoft.com/en-us/windows-hardware/test/wpt/memory-footprint-optimization)
- Commitment does not imply residency: `VirtualAlloc(MEM_COMMIT)` allocates commit charges, and physical pages need not be assigned until the addresses are accessed. A reserved range alone does not allocate physical storage. [Microsoft: VirtualAlloc](https://learn.microsoft.com/en-us/windows/win32/api/memoryapi/nf-memoryapi-virtualalloc)
- In page-level analysis, `PSAPI_WORKING_SET_EX_BLOCK.Shared` means the page **can** be shared, and `ShareCount` describes how many processes share it (saturating at 7). These are distinct properties. [Microsoft: PSAPI_WORKING_SET_EX_BLOCK](https://learn.microsoft.com/en-us/windows/win32/api/psapi/ns-psapi-psapi_working_set_ex_block)
- Image-backed does not always mean shared: a modified copy-on-write image page becomes private, although `VirtualQueryEx` still reports `MEM_IMAGE`; the page's working-set Shared bit distinguishes the private copy. [Microsoft: VirtualQueryEx](https://learn.microsoft.com/en-us/windows/win32/api/memoryapi/nf-memoryapi-virtualqueryex)
- Existing visible-production snapshot: 9,822,208 bytes total WS = **9.367 MiB**, 978,944 bytes private WS = **0.934 MiB**, and 1,413,120 bytes private commit = **1.348 MiB**. These values are local observations, not guarantees. [Local benchmark](../../benchmarks/memory-ascii-chrome.json)
- The same snapshot attributes 1,972 KiB resident to ntdll, 884 KiB to KERNELBASE, 492 KiB to USER32, 676 KiB to MSCTF, 624 KiB to combase, and 488 KiB to RPCRT4. The first three alone sum to 3,348 KiB in that snapshot. This is residency, not the entire mapped image size and not proof of unique physical RAM owned by this application. [Local benchmark](../../benchmarks/memory-ascii-chrome.json)

### Inferences

- Shared DLL pages must remain counted for the user's **total WS** criterion. Their presence does not mean every process mapping them consumes an additional physical copy; summing total working sets across processes can count the same physical page repeatedly. This follows from shared physical pages being visible in multiple processes. [Microsoft: Scope of Allocated Memory](https://learn.microsoft.com/en-us/windows/win32/memory/scope-of-allocated-memory); [Microsoft: WorkingSet64](https://learn.microsoft.com/en-us/dotnet/api/system.diagnostics.process.workingset64?view=netframework-4.7.2)
- A 0.934 MiB private WS result cannot be presented as “the app uses less than 3 MB total.” The actual total in this run exceeds both 3 MB decimal and 3 MiB. [Local benchmark](../../benchmarks/memory-ascii-chrome.json)

### Gaps

- The JSON snapshot does not quantify incremental, uniquely attributable system-wide physical memory, GPU/compositor memory, cached file costs, or supporting-service memory. Microsoft explicitly warns that per-process WS omits such supporting costs. [Microsoft: Reference sets](https://learn.microsoft.com/en-us/windows-hardware/test/wpt/wpa-reference-set)
- No single “Memory” column label should be assumed to mean total WS without validating the particular tool and column. The acceptance measurement should name the API/counter and units explicitly. This is a measurement recommendation based on the distinct documented counters. [Microsoft: PROCESS_MEMORY_COUNTERS_EX2](https://learn.microsoft.com/en-us/windows/win32/api/psapi/ns-psapi-process_memory_counters_ex2)

## Can a Windows 11 desktop application have a guaranteed maximum of 2–3 MB?

### Takeaway

The measured build does not meet the target, and the research does not establish a universal Windows desktop floor that proves the target impossible. Windows has an explicit hard maximum-working-set mechanism, but making its counter stay small is a different engineering outcome from demonstrating a small, responsive editor workload. [Local benchmark](../../benchmarks/memory-ascii-chrome.json); [Microsoft: SetProcessWorkingSetSizeEx](https://learn.microsoft.com/en-us/windows/win32/api/memoryapi/nf-memoryapi-setprocessworkingsetsizeex)

### Cited Findings

- `SetProcessWorkingSetSizeEx` documents `QUOTA_LIMITS_HARDWS_MAX_ENABLE` as enforcing the maximum. Without hard enforcement, abundant memory can allow WS above the requested maximum. Its min/max arguments are paging-policy settings. The documented minimum argument is rounded up to 20 pages when positive but smaller than 20 pages; this is **not** a statement that a GUI requires 20 pages, 2 MB, 7 MB, or 10 MB. The documented maximum argument must satisfy the API's bounds. [Microsoft: SetProcessWorkingSetSizeEx](https://learn.microsoft.com/en-us/windows/win32/api/memoryapi/nf-memoryapi-setprocessworkingsetsizeex)
- The non-Ex API does not guarantee that requested memory will be reserved or remain resident. The OS can shrink an idle application's working set or shrink it under memory pressure. [Microsoft: SetProcessWorkingSetSize](https://learn.microsoft.com/en-us/windows/win32/api/memoryapi/nf-memoryapi-setprocessworkingsetsize)
- WS is a point-in-time property affected by machine state, RAM capacity, memory pressure, and OS trimming. Microsoft recommends scenario reference sets for understanding system-wide memory impact. [Microsoft: Reference sets](https://learn.microsoft.com/en-us/windows-hardware/test/wpt/wpa-reference-set)
- Existing minimal-window benchmark reports 6,795,264 total WS bytes (6.480 MiB), 708,608 private WS bytes, and 1,101,824 private commit bytes. This is a particular local process/run; its JSON alone does not prove visibility, launch flags, input activity, or a universal lower bound. [Local historical benchmark](../../benchmarks/memory-floor.json)
- Existing startup probe records `show=10`, `startupFlags=0`, and `startupShowWindow=0`. Microsoft says `wShowWindow` is ignored unless `STARTF_USESHOWWINDOW` is set; `SW_SHOWDEFAULT` is value 10. Thus, an outer script option named “Hidden,” or a zero `wShowWindow` field without the flag, is insufficient evidence of a hidden UI. [Local probe](../../benchmarks/probe-startup-flags.json); [Microsoft: STARTUPINFOW](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/ns-processthreadsapi-startupinfow); [Microsoft: ShowWindow](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-showwindow)

### Inferences

- A promise of “always at most 2–3 MB total WS, responsive during all editing, on Windows 11 x64” is **not supported** by the current evidence. The appropriate conclusion is “unproven and not met by the current visible build,” rather than “Windows universally requires at least 7/10 MB.” [Local benchmark](../../benchmarks/memory-ascii-chrome.json); [Microsoft: Reference sets](https://learn.microsoft.com/en-us/windows-hardware/test/wpt/wpa-reference-set)
- It would also be incorrect to claim the OS offers no way to enforce such a WS number: a successfully applied hard maximum is a documented capability. Its practical suitability at 2–3 MB requires measurement. A limit applied after entry-point execution cannot retroactively make an earlier startup peak disappear; lifetime peak and startup coverage matter for a maximum requirement. [Microsoft: SetProcessWorkingSetSizeEx](https://learn.microsoft.com/en-us/windows/win32/api/memoryapi/nf-memoryapi-setprocessworkingsetsizeex); [Microsoft: PROCESS_MEMORY_COUNTERS_EX2](https://learn.microsoft.com/en-us/windows/win32/api/psapi/ns-psapi-process_memory_counters_ex2)
- A genuinely hidden bare Win32 test, even when correctly established, should be described only as that baseline. It does not validate a visible, interactive Unicode editor. Report hidden and visible scenarios separately and verify actual visibility rather than trusting launch-option names. [Microsoft: STARTUPINFOW](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/ns-processthreadsapi-startupinfow); [Local probe](../../benchmarks/probe-startup-flags.json)

### Gaps

- No authoritative source was found establishing a universal minimum total WS for every responsive Unicode Windows 11 GUI editor. Microsoft API min/default values do not establish one. [Microsoft: SetProcessWorkingSetSizeEx](https://learn.microsoft.com/en-us/windows/win32/api/memoryapi/nf-memoryapi-setprocessworkingsetsizeex)
- No 2–3 MB capped experiment with Vietnamese composition, visible repaint, multiple documents, file dialogs, undo, and optional MCP was performed in this research. Responsiveness and correctness under that cap remain unknown. Existing uncapped measurements are inadequate to infer those results. [Local benchmark](../../benchmarks/memory-ascii-chrome.json)
- An unlimited number/size of live documents cannot have a meaningful unconditional resource promise. A testable contract needs file-count/size, undo, preview, and MCP scenario bounds; this is a proposed acceptance condition, not a Microsoft-prescribed limit.

## Does trimming reduce real cost, and how should the target be validated?

### Takeaway

Do not use repeated trimming or post-trim idle screenshots as evidence of a smaller responsive application footprint. Preserve total WS as the acceptance metric, pair it with peak/latency/fault data during representative foreground work, and use a separate system-wide measurement when the question is actual RAM impact. [Microsoft: Working Set](https://learn.microsoft.com/en-us/windows/win32/memory/working-set); [Microsoft: Reference sets](https://learn.microsoft.com/en-us/windows-hardware/test/wpt/wpa-reference-set)

### Cited Findings

- `EmptyWorkingSet` removes as many WS pages as possible; passing `(SIZE_T)-1` for both bounds to the working-set-size APIs has the same trimming purpose. Microsoft describes emptying as useful primarily for testing and tuning. It does not state that it frees application allocations or reduces commit. [Microsoft: EmptyWorkingSet](https://learn.microsoft.com/en-us/windows/win32/api/psapi/nf-psapi-emptyworkingset); [Microsoft: Working Set Information](https://learn.microsoft.com/en-us/windows/win32/psapi/working-set-information)
- Touching a pageable page absent from the working set causes a fault. Soft faults can find data already resident in another process or transition/cache state; hard faults require backing-store reads. Removing a shared page from one process does not remove it from other processes. Pages removed from all working sets may remain physically cached in transition until reused or repurposed. Reaching a maximum WS may require removing a resident page to make room for a new one. [Microsoft: Working Set](https://learn.microsoft.com/en-us/windows/win32/memory/working-set)
- Page-level `QueryWorkingSet`/`QueryWorkingSetEx` information is a snapshot of pages physically present at the instant queried; working-set monitoring can identify pages added during operations. [Microsoft: Working Set Information](https://learn.microsoft.com/en-us/windows/win32/psapi/working-set-information)
- `GetProcessMemoryInfo` supports the ordinary, extended, and EX2 memory counter structures. [Microsoft: GetProcessMemoryInfo](https://learn.microsoft.com/en-us/windows/win32/api/psapi/nf-psapi-getprocessmemoryinfo)
- VMMap reports committed virtual memory by type together with the physical WS assigned to those types; it supports exported data and command-line scripting. [Microsoft Sysinternals: VMMap](https://learn.microsoft.com/en-us/sysinternals/downloads/vmmap)
- Microsoft advises balancing resource/cache release against responsiveness. Its memory guidance recommends traces to find allocation sources and establishing a steady-state benchmark when checking leaks. [Microsoft: Improve app performance by reducing memory and disk use](https://learn.microsoft.com/en-us/windows/apps/develop/performance/disk-memory)

### Inferences

- Trimming can substantially lower the process's WS counter without eliminating its allocations, shared physical pages, or future need for the evicted code/data. Under a cap smaller than the active workload, page churn can add CPU overhead and, if backing storage is required, latency. The magnitude is workload-dependent: soft faults are not equivalent to disk faults, and poor responsiveness is a risk to measure rather than an automatic conclusion. [Microsoft: Working Set](https://learn.microsoft.com/en-us/windows/win32/memory/working-set); [Microsoft: EmptyWorkingSet](https://learn.microsoft.com/en-us/windows/win32/api/psapi/nf-psapi-emptyworkingset)
- Recommended acceptance protocol: use a visible foreground window; name OS build, bitness, exact build, page size, units, launch method, and scenario bounds; capture raw total `WorkingSetSize` and lifetime `PeakWorkingSetSize`, while reporting private WS and private commit separately. Exercise startup, Vietnamese input/composition, repaint/resize/scroll, typing/undo, switching/opening/saving files, and MCP off/on. Record interaction latency, CPU, and soft/hard fault activity against an uncapped control. This is a proposed protocol based on the documented counters and WS behavior, not a claim these tests have already passed. [Microsoft: PROCESS_MEMORY_COUNTERS_EX2](https://learn.microsoft.com/en-us/windows/win32/api/psapi/ns-psapi-process_memory_counters_ex2); [Microsoft: Working Set Information](https://learn.microsoft.com/en-us/windows/win32/psapi/working-set-information)
- Sampling alone may miss short spikes. Treat the lifetime peak as an additional check for “maximum,” and do not start observing only after a trim. Count any editor helper/MCP process in a declared application boundary; otherwise moving work out of the main PID only moves the measurement boundary. These are measurement recommendations. [Microsoft: PROCESS_MEMORY_COUNTERS_EX2](https://learn.microsoft.com/en-us/windows/win32/api/psapi/ns-psapi-process_memory_counters_ex2); [Microsoft: Reference sets](https://learn.microsoft.com/en-us/windows-hardware/test/wpt/wpa-reference-set)
- For actual physical system impact, add WPA reference-set analysis. Microsoft documents `wpr -start referenceset -filemode` and `wpr -stop file-name.etl`, requiring elevation. This tracing deliberately empties working sets system-wide at collection start, so it belongs in a dedicated comparison experiment, not a normal unperturbed WS acceptance run. It was not run here. [Microsoft: Reference sets](https://learn.microsoft.com/en-us/windows-hardware/test/wpt/wpa-reference-set)
- Practical recommendation: continue genuine reductions in loaded code/data and unnecessary allocations, but do not promise the requested 2–3 MB maximum from the present evidence. A hard cap is an experimental option to investigate explicitly, with results labeled as capped, including startup and responsiveness; routine trimming should not be shipped merely to make the displayed number smaller. This recommendation follows from the current 9.367 MiB result and the documented distinction between residency policy, faults, and allocation cost. [Local benchmark](../../benchmarks/memory-ascii-chrome.json); [Microsoft: SetProcessWorkingSetSizeEx](https://learn.microsoft.com/en-us/windows/win32/api/memoryapi/nf-memoryapi-setprocessworkingsetsizeex)

### Gaps

- An exact universally reliable page-fault/latency budget cannot be inferred from documentation. Such budgets must be chosen for the product and measured on the target configuration.
- Total WS is the requested metric, but not a complete ledger of physical memory attributable to all supporting components. Even a hard-capped process is not proof of a matching cap on system-wide RAM cost. [Microsoft: Reference sets](https://learn.microsoft.com/en-us/windows-hardware/test/wpt/wpa-reference-set)
