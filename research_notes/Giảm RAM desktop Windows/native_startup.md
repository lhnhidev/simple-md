# Native Windows startup and runtime architecture for simple-md

## Can a complete native editor credibly stay below 2–3 MB total working set?

### Takeaway

There is no primary-source evidence here that a complete, visible, accessible Windows editor with normal Vietnamese input and shell dialogs can reliably stay below 2–3 MB total working set. Native Win32 with deferred subsystems remains the strongest architecture to investigate, but an empty startup-window saving must be reported separately from an operational editor.

### Cited Findings

- Windows working set means the process's pageable virtual pages currently resident in physical RAM. Touching absent pages adds them back; trimming and OS memory pressure affect the result. Shared pages can occur in several processes' working sets simultaneously. Consequently, a smaller trimmed snapshot is not evidence of a smaller actively used feature set. — [Working Set](https://learn.microsoft.com/en-us/windows/win32/memory/working-set)
- `WorkingSetSize`, `PrivateUsage` (private commit), and `PrivateWorkingSetSize` are explicitly different fields. The target must use `WorkingSetSize`; private working set or private bytes cannot substitute for it. — [PROCESS_MEMORY_COUNTERS_EX2](https://learn.microsoft.com/en-us/windows/win32/api/psapi/ns-psapi-process_memory_counters_ex2)
- Microsoft cautions that a process working set does not include every supporting resource, such as system-service memory, and depends heavily on machine state and trimming policy. This matters when comparing a shared host with a standalone process. — [Reference sets and system-wide effects](https://learn.microsoft.com/en-us/windows-hardware/test/wpt/wpa-reference-set)
- The inspected build already uses `/O1 /GL /MT`, `/LTCG /OPT:REF /OPT:ICF`, and delay imports for ole32, shell32, comdlg32, and advapi32. Main already loads Msftedit lazily through `EnsureRich()` and initializes COM lazily through `EnsureCom()`. — [Local build.ps1](../../build.ps1); [Local main.cpp](../../src/main.cpp)
- `/OPT:REF` discards unreferenced packaged functions/data; `/OPT:ICF` folds duplicate COMDATs. ICF can give distinct functions/data the same address, so identity-by-address assumptions need attention. — [/OPT](https://learn.microsoft.com/en-us/cpp/build/reference/opt-optimizations?view=msvc-170)
- `/MT` selects the static multithread runtime; `/MD` uses the runtime DLL. This defines a linkage choice, not a documented promise that either gives lower total working set. — [/MD, /MT, /LD](https://learn.microsoft.com/en-us/cpp/build/reference/md-mt-ld-use-run-time-library?view=msvc-170)
- `/DELAYLOAD` postpones a DLL until the first imported call. It is intended for functionality that may never be used or is used late. `/DELAY:NOBIND` omits a bound IAT and saves image-file space. These mechanisms do not promise control over dependencies loaded indirectly by Windows. — [Linker support for delay-loaded DLLs](https://learn.microsoft.com/en-us/cpp/build/reference/linker-support-for-delay-loaded-dlls?view=msvc-170)
- `/ORDER` can group related/frequently called COMDAT functions to improve paging locality. This is a measured image-layout experiment, not a way to eliminate mandatory OS code. — [/ORDER](https://learn.microsoft.com/en-us/cpp/build/reference/order-put-functions-in-order?view=msvc-170)
- A system `EDIT` supports Unicode, multiline editing, selection, scrolling, and a system-managed text buffer; RichEdit adds features unavailable in the simpler control. This supports testing `EDIT` for plain Markdown source, but does not establish a RAM advantage or feature parity. — [About Edit Controls](https://learn.microsoft.com/en-us/windows/win32/controls/about-edit-controls)

### Inferences

- Best production direction: retain native Win32 and existing lazy RichEdit/COM boundaries, profile resident pages by module and by feature transition, then optimize only pages actually touched. The tiny private-resident observation suggests that several-megabyte savings will require avoiding OS subsystem activation, not merely reducing C++ container allocations. This is an inference, not a documented lower bound. — [Working Set](https://learn.microsoft.com/en-us/windows/win32/memory/working-set); [Local main.cpp](../../src/main.cpp)
- `/MD` can reduce duplicated runtime code across multiple modules, while `/MT` permits unreferenced static routines to disappear under link optimization. The actual total working set can favor either on this machine; keep the choice behind a reproducible experiment and include redistribution/deployment implications. — [/MD versus /MT](https://learn.microsoft.com/en-us/cpp/build/reference/md-mt-ld-use-run-time-library?view=msvc-170); [/OPT](https://learn.microsoft.com/en-us/cpp/build/reference/opt-optimizations?view=msvc-170)
- A shared host can amortize existing runtime and UI costs across documents/windows. It does not remove the host's RAM, and resident shared DLL pages still appear in each process that touches them. Report total host/process-tree cost and incremental cost separately; never claim that moving features to another process meets the app's total-RAM budget. — [Working Set](https://learn.microsoft.com/en-us/windows/win32/memory/working-set); [Reference sets](https://learn.microsoft.com/en-us/windows-hardware/test/wpt/wpa-reference-set)
- A hard resident ceiling achieved by frequent trimming changes residency and may cause renewed faults during editing. It is outside the requested architecture goal of reaching the budget without paging/trimming tricks. — [Working Set](https://learn.microsoft.com/en-us/windows/win32/memory/working-set)

### Gaps

- Coordinator-supplied observations, not independently reproduced in this research: the normal empty visible app was 9.37 MiB total / 0.93 MiB private resident; the noneditable lean prototype reached 6.87 MiB total; x86 and removed-supportedOS-manifest experiments were worse. These are local experimental observations, not portable Windows minimums.
- No primary source found specifies a minimum total working set for visible Win32, RichEdit, TSF, Vietnamese IME, UI Automation, or the Common Item Dialog. No credible citation establishes universal impossibility at 2–3 MB; the correct conclusion is unsubstantiated and contradicted by the available local prototypes, not mathematically impossible.
- No equivalent functional benchmark exists for a lean shell with screen reader, complete keyboard navigation, Vietnamese text entry, DPI changes, real file dialogs, MCP, and post-use steady state. Therefore 6.87 MiB cannot be accepted as the finished app's footprint.
- No hidden-window control result establishes a visible baseline. The coordinator reports PowerShell WindowStyle was ignored; future tests must verify actual visibility, foreground activation, state, and post-interaction residency.

## Which input, accessibility, and DPI optimizations are safe?

### Takeaway

Per-window input-context association is a supported reversible tool, but it is not documented as a way to prevent loading the Windows text-input stack. Thread-level IME disabling is suitable only for a truly noneditable startup thread; preserve normal input on a fresh editor thread and avoid unsupported text-rendering shortcuts.

### Cited Findings

- `ImmDisableIME` disables IME for a thread or all threads in a process. It must run before the thread's first top-level window receives `WM_CREATE`, including before CreateWindow or during `WM_NCCREATE`. The current page has an incomplete unnamed parameter description, so it does not fully document flag/value details. — [ImmDisableIME](https://learn.microsoft.com/en-us/windows/win32/api/imm/nf-imm-immdisableime)
- `ImmAssociateContext` changes an HWND's associated input context and returns the previous association. New windows normally receive a default context. — [ImmAssociateContext](https://learn.microsoft.com/en-us/windows/win32/api/imm/nf-imm-immassociatecontext)
- `ImmAssociateContextEx(..., IACE_DEFAULT)` restores the default input context. `IACE_CHILDREN` affects only existing child windows created by the same thread; subsequently created children receive the normal default context. — [ImmAssociateContextEx](https://learn.microsoft.com/en-us/windows/win32/api/imm/nf-imm-immassociatecontextex)
- TSF activation is explicitly per calling thread, and its Activate/Deactivate calls must balance on that same thread. This does not document reversal of `ImmDisableIME` or guarantee that a direct Activate call repairs a disabled thread. — [ITfThreadMgr::Activate](https://learn.microsoft.com/en-us/windows/win32/api/msctf/nf-msctf-itfthreadmgr-activate)
- The older `ImmDisableTextFrameService` is unavailable from Vista onward and Microsoft directs callers to ImmDisableIME. It is not a modern alternate optimization. — [ImmDisableTextFrameService](https://learn.microsoft.com/en-us/windows/win32/api/imm/nf-imm-immdisabletextframeservice)
- **`ETO_IGNORELANGUAGE` is reserved for system use.** Microsoft warns of lost international script support and possibly missing text, says it inhibits font fallback, and says it should not be passed. An ASCII-only branch does not make a reserved flag a supported production contract. — [ExtTextOutW](https://learn.microsoft.com/en-us/windows/win32/api/wingdi/nf-wingdi-exttextoutw)
- Microsoft supplies UI Automation providers for standard Win32 controls. Custom controls need providers to expose semantics and functionality; pixels alone do not expose individual buttons or text content. — [UI Automation Providers Overview](https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-providersoverview)
- A complex custom control needs accessible element navigation, properties, focus, geometry, and relevant control patterns. This is additional implementation work for an all-painted shell/editor. — [Server-side UI Automation provider](https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-serversideprovider)
- Microsoft recommends process DPI awareness in the manifest. Setting process awareness through an API must precede any HWND creation; changing it afterwards is unsupported. — [Default DPI awareness](https://learn.microsoft.com/en-us/windows/win32/hidpi/setting-the-default-dpi-awareness-for-a-process)
- `WM_DPICHANGED` supplies a new DPI and a suggested rectangle, which applications should apply while updating fonts/layout. — [WM_DPICHANGED](https://learn.microsoft.com/en-us/windows/win32/hidpi/wm-dpichanged)

### Inferences

- A safe low-risk experiment is per-HWND context deferral on a noneditable landing window and restoring the default association before any input field is used. Measure whether this avoids any module faults at all. Do not infer a TSF load guarantee from the association API: its contract only concerns associations. — [ImmAssociateContextEx](https://learn.microsoft.com/en-us/windows/win32/api/imm/nf-imm-immassociatecontextex)
- Treat a thread passed to ImmDisableIME as permanently noneditable for the application's lifetime: no supported inverse was found. A new normal GUI thread is a defensible experiment; loading an editor DLL and creating its control on the disabled thread is not a safe recovery plan. Never use process-wide disabling in this design. — [ImmDisableIME](https://learn.microsoft.com/en-us/windows/win32/api/imm/nf-imm-immdisableime); [TSF thread activation](https://learn.microsoft.com/en-us/windows/win32/api/msctf/nf-msctf-itfthreadmgr-activate)
- The present lean probe is an architectural probe, not a feature-complete alternative: all its apparent buttons are painted disabled boxes, it has no editor, and it uses ETO_IGNORELANGUAGE. It also lacks the production WM_DPICHANGED handling seen in main. Integrating actual standard buttons, full text output, accessibility, and input may reduce or erase savings. — [Local lean-shell.cpp](../../tests/lean-shell.cpp); [Local main.cpp](../../src/main.cpp); [UIA providers](https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-providersoverview)
- Keep PerMonitorV2 in the EXE manifest and implement DPI changes in both shell and editor windows. Copy the actual window's latest bounds at handover; do not assume startup system DPI still matches its current monitor. — [Default DPI awareness](https://learn.microsoft.com/en-us/windows/win32/hidpi/setting-the-default-dpi-awareness-for-a-process); [WM_DPICHANGED](https://learn.microsoft.com/en-us/windows/win32/hidpi/wm-dpichanged)

### Gaps

- No supported inverse of ImmDisableIME, nor a documented guarantee that a newly created thread after only another thread was disabled has every desired third-party IME interaction, was found. Normal-thread behavior must be validated with the actual Windows Vietnamese Telex/VNI and user-installed input method, composition, correction, paste, undo, switching focus, and screen-reader use.
- No public supported switch was found that guarantees a visible activated HWND avoids textinputframework/MSCTF while preserving the complete input stack. Per-window deferral therefore remains a measured hypothesis.
- The reported ASCII ETO_IGNORELANGUAGE saving is an unsupported experiment and should not become a product requirement or supported implementation recommendation.

## How should an experimental lean shell and lazy editor DLL be structured?

### Takeaway

If pursued, use a small no-CRT bootstrap only for a functional noneditable landing window, then create an entirely new normal editor GUI thread/window through a C ABI. This architecture can defer costs until activation; it cannot be presented as keeping a fully active editor under the shell's idle RAM number.

### Cited Findings

- Any thread may create a window, but the creating thread owns it and its message queue, and must pump messages. A UI thread waiting for handles must use a message-aware wait to avoid deadlock. — [Creating Windows in Threads](https://learn.microsoft.com/en-us/windows/win32/procthread/creating-windows-in-threads)
- A thread cannot destroy an HWND created by a different thread. — [DestroyWindow](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-destroywindow)
- DllMain runs under loader-lock restrictions. Microsoft discourages loading modules, COM initialization, cross-thread synchronization, UI calls, and thread creation there; put complex work in an exported initialization function after LoadLibrary returns. — [DLL best practices](https://learn.microsoft.com/en-us/windows/win32/dlls/dynamic-link-library-best-practices)
- Code using the CRT should use `_beginthreadex`/`_endthreadex` rather than raw thread startup/termination; returning from the `_beginthreadex` procedure performs appropriate thread cleanup, and its handle must be closed explicitly. — [CreateThread](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-createthread); [_beginthreadex](https://learn.microsoft.com/en-us/cpp/c-runtime-library/reference/beginthread-beginthreadex?view=msvc-170)
- CRT FILE objects, allocation ownership, locales, and other runtime state must not be passed between separate runtime copies as if interchangeable. Allocating through one CRT and freeing through another can corrupt the heap. — [CRT objects across DLL boundaries](https://learn.microsoft.com/en-us/cpp/c-runtime-library/potential-errors-passing-crt-objects-across-dll-boundaries?view=msvc-170)
- Bypassing CRT startup with a custom `/ENTRY` requires correct security-cookie initialization before protected code executes. Microsoft warns that an uninitialized default cookie weakens overrun protection. — [__security_init_cookie](https://learn.microsoft.com/en-us/cpp/c-runtime-library/reference/security-init-cookie?view=msvc-170)
- DLL unloading follows reference counts. A thread executing inside its own DLL cannot safely call FreeLibrary then ExitThread separately; the combined API exists to avoid that race. — [FreeLibrary](https://learn.microsoft.com/en-us/windows/win32/api/libloaderapi/nf-libloaderapi-freelibrary); [FreeLibraryAndExitThread](https://learn.microsoft.com/en-us/windows/win32/api/libloaderapi/nf-libloaderapi-freelibraryandexitthread)
- `LoadLibraryEx` supports absolute module paths and per-call search flags for dependencies, including DLL-load directory and System32. — [LoadLibraryExW](https://learn.microsoft.com/en-us/windows/win32/api/libloaderapi/nf-libloaderapi-loadlibraryexw)
- Common Item Dialog requires COM initialization before creating its COM object; UI threads should use STA (`COINIT_APARTMENTTHREADED`). The modern dialog exposes shell namespaces and normal Open/Save behavior. — [Common Item Dialog](https://learn.microsoft.com/en-us/previous-versions/windows/desktop/legacy/bb776913%28v%3Dvs.85%29)
- Child-process standard input/output redirection requires deliberate handle inheritance and closing unused pipe ends. Adding a separate process introduces lifetime and EOF obligations rather than free isolation. — [Redirected child process I/O](https://learn.microsoft.com/en-us/windows/win32/procthread/creating-a-child-process-with-redirected-input-and-output)
- The local WIP core ABI is already C-compatible and size-tagged, but `SimpleMdGui` is a synchronous entry that executes RunApplication on its caller's thread. Its ready callback executes there too. The API currently does not itself create a normal editor thread. — [Local core-api.h](../../src/core-api.h); [Local main.cpp](../../src/main.cpp)

### Inferences

Recommended experimental state machine, contingent on measurable benefit:

1. **Bootstrap.** Parse mode before creating any GUI; `--mcp` must take a dedicated stdio path. For GUI mode, create a keyboard-accessible noneditable landing window with genuine New/Open commands. Disable IME only on that landing thread if the experiment needs it. Keep normal Unicode GDI output and the DPI manifest. — [ImmDisableIME](https://learn.microsoft.com/en-us/windows/win32/api/imm/nf-imm-immdisableime); [ExtTextOutW](https://learn.microsoft.com/en-us/windows/win32/api/wingdi/nf-wingdi-exttextoutw); [Local core API](../../src/core-api.h)
2. **Activation.** Atomically permit one in-flight activation. Keep the landing thread pumping messages while loading the core DLL through a native bootstrap worker that uses only Win32 services. After LoadLibrary returns, an exported start function in the initialized core can create the CRT-using GUI thread with `_beginthreadex`. A simpler synchronous load on the landing thread may hitch; it should not be described as guaranteed responsive. No load, thread creation, or COM work in DllMain. — [DLL best practices](https://learn.microsoft.com/en-us/windows/win32/dlls/dynamic-link-library-best-practices); [Creating Windows in Threads](https://learn.microsoft.com/en-us/windows/win32/procthread/creating-windows-in-threads); [_beginthreadex](https://learn.microsoft.com/en-us/cpp/c-runtime-library/reference/beginthread-beginthreadex?view=msvc-170)
3. **Create a new editor HWND.** The normal GUI thread owns the root, children, focus, RichEdit and dialogs; do not attempt to transfer the existing HWND between threads. Initialize STA on the dialog-owning editor thread when needed. Copy launch strings into core-owned memory before a shell launch structure can expire. Pass only plain values, HWNDs, immutable copied strings, and explicit ownership through the C ABI; never std::string/std::vector/FILE or exceptions across it. — [Window ownership](https://learn.microsoft.com/en-us/windows/win32/procthread/creating-windows-in-threads); [CRT boundaries](https://learn.microsoft.com/en-us/cpp/c-runtime-library/potential-errors-passing-crt-objects-across-dll-boundaries?view=msvc-170); [Common Item Dialog](https://learn.microsoft.com/en-us/previous-versions/windows/desktop/legacy/bb776913%28v%3Dvs.85%29)
4. **Handover.** Read bounds/state on the shell thread, create and paint the editor, then post a ready notification back to the shell thread. Only that shell thread hides/destroys its own window. Marshal callbacks rather than letting the current `ready` callback directly mutate shell state from the editor thread. Avoid synchronous cross-thread calls and permanent AttachThreadInput coupling; activation, Alt-Tab/taskbar continuity, maximized placement, dragging between monitors, failed loads and cancellation all need explicit handling. — [DestroyWindow](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-destroywindow); [Creating Windows in Threads](https://learn.microsoft.com/en-us/windows/win32/procthread/creating-windows-in-threads); [Local ready callback](../../src/main.cpp)
5. **Keep the core loaded for the editor session.** The safe first implementation retains its module handle until all GUI/MCP threads, windows, WndProcs/subclasses, hooks, timers, UIA providers, COM references, and queued callbacks are finished. Avoid aggressive unload/reload merely to lower a counter. Only unload after an explicit quiescence protocol, from host code that remains mapped. A no-CRT shell must not call ExitProcess when its shell WM_DESTROY ends the landing message loop while the editor is still running. — [DLL lifecycle guidance](https://learn.microsoft.com/en-us/windows/win32/dlls/dynamic-link-library-best-practices); [FreeLibraryAndExitThread](https://learn.microsoft.com/en-us/windows/win32/api/libloaderapi/nf-libloaderapi-freelibraryandexitthread); [_beginthreadex process-exit semantics](https://learn.microsoft.com/en-us/cpp/c-runtime-library/reference/beginthread-beginthreadex?view=msvc-170)
6. **Measure complete states.** Publish separate total working-set figures for first visible/foreground landing state, after New + Vietnamese input, after preview, after Open/Save dialogs, and after stdio MCP activity. The new thread loads its normal input stack, so initial-shell savings are deferred costs rather than a finished-editor RAM result. — [Working Set](https://learn.microsoft.com/en-us/windows/win32/memory/working-set); [TSF activation](https://learn.microsoft.com/en-us/windows/win32/api/msctf/nf-msctf-itfthreadmgr-activate)

For MCP, prefer a small explicit `--mcp` mode that uses inherited standard handles and never creates a landing GUI, loads RichEdit, or initializes GUI COM. A future executable split could keep the MCP process's import graph independent of User32/GDI; measure all processes and preserve exact client configuration/stdio behavior. In a DLL design, core code must open/use its own CRT streams from inherited OS handles rather than receiving shell FILE pointers. — [CRT boundaries](https://learn.microsoft.com/en-us/cpp/c-runtime-library/potential-errors-passing-crt-objects-across-dll-boundaries?view=msvc-170); [Standard-handle inheritance](https://learn.microsoft.com/en-us/windows/win32/procthread/creating-a-child-process-with-redirected-input-and-output)

A separate launcher process is easier to isolate from the editor's IME lifetime but duplicates process/runtime costs during overlap, complicates argument/error/stdio routing and taskbar transitions, and does not establish a smaller active editor. Prefer the current single GUI process unless a controlled native-shell experiment demonstrates useful empty-startup savings with full functionality. — [Working Set](https://learn.microsoft.com/en-us/windows/win32/memory/working-set); [Redirected process I/O](https://learn.microsoft.com/en-us/windows/win32/procthread/creating-a-child-process-with-redirected-input-and-output)

### Gaps

- The core ABI is WIP uncommitted source. No integrated frontend, DLL lifetime protocol, responsive loader, thread-handover tests, or accessibility acceptance result was inspected. No code, Git state, settings, or UI was changed during this research.
- The exact gain from a supported no-CRT shell after removing ETO_IGNORELANGUAGE, adding accessible controls, and preserving normal activation is unknown. The implementation complexity is high relative to the available sub-3-MB evidence.
- The stronger requirement of a 2–3 MB maximum during actual editing and ordinary dialogs remains unmet. A defensible recommendation is to state this limit plainly, keep the functional native editor, and use the shell experiment only as an optional startup optimization with honest before/after feature-state measurements.
