# Document/editor memory patterns for simple-md

Research date: 2026-10-29. Read-only inspection of the current source; recommendations are designs to measure, not implemented changes. Numbers supplied by the coordinator (9.37 MiB total/0.93 MiB private resident empty; about 23 MiB total with a 1.78 MB file) have not been independently remeasured here.

## 1. Which existing allocations should be removed first, and what would that improve?

### Takeaway

Keep RichEdit as the authoritative editing buffer first. Remove repeated full-file copies, decode-free fingerprint checks, and whole-document MCP extraction before considering a replacement editor; these mainly reduce loaded-document peaks and temporary allocation churn, with almost no effect on a never-opened empty window.

### Cited Findings

- `ReadDocument` allocates the complete encoded file, computes its fingerprint, makes `bytes.substr(offset)` for UTF-8 decoding, constructs UTF-16, then replaces that with another `NormalizeLf` result. UTF-16 validation calls `Utf8(d.text)` solely for validation, allocating a complete throwaway encoded copy. [Local document.cpp:24](/D:/workspace/simple-md/src/document.cpp:24), [mcp.cpp:7](/D:/workspace/simple-md/src/mcp.cpp:7).
- `NormalizeLf` always allocates and reserves `text.size()` even when there is no CR. `EditorLines` first makes another normalized string and then a CRLF string. `Editor` calls `SetRichText(EditorLines(text))`, so loading contains another conversion stage before RichEdit retains its own text. [Local document.cpp:12](/D:/workspace/simple-md/src/document.cpp:12), [main.cpp:163](/D:/workspace/simple-md/src/main.cpp:163).
- `ControlText` allocates a full UTF-16 copy from RichEdit and returns a separately allocated normalized copy. Saving obtains this text, `EncodeDocument` creates another line-ending-normalized UTF-16 copy, then creates all output bytes before `AtomicWrite`. The original atomic replacement and error handling are already explicit. [Local main.cpp:38](/D:/workspace/simple-md/src/main.cpp:38), [main.cpp:226](/D:/workspace/simple-md/src/main.cpp:226), [document.cpp:46](/D:/workspace/simple-md/src/document.cpp:46).
- Both the pre-save external conflict check and `WM_ACTIVATEAPP` external-change check call `ReadDocument`; therefore unchanged files are fully read, decoded, Unicode-validated, and normalized just to compare fingerprints. [Local main.cpp:240](/D:/workspace/simple-md/src/main.cpp:240), [main.cpp:248](/D:/workspace/simple-md/src/main.cpp:248), [main.cpp:443](/D:/workspace/simple-md/src/main.cpp:443).
- RichEdit `EM_STREAMIN` repeatedly requests chunks from an application callback; it supports plain Unicode text. `EM_STREAMOUT` repeatedly supplies chunks to a callback, which can write directly to a file. [Microsoft EM_STREAMIN](https://learn.microsoft.com/en-us/windows/win32/controls/em-streamin), [Microsoft EM_STREAMOUT](https://learn.microsoft.com/en-us/windows/win32/controls/em-streamout).
- `read_document` accepts a bounded page, yet calls `Load`, copies the entire document through `ControlText`, scans all code points, makes a selected substring, and UTF-8-encodes it. The pipe/server then builds a JSON DOM and serialized reply; the returned content is itself `result.dump()` nested in an outer tool result. [Local main.cpp:321](/D:/workspace/simple-md/src/main.cpp:321), [main.cpp:340](/D:/workspace/simple-md/src/main.cpp:340), [mcp.cpp:89](/D:/workspace/simple-md/src/mcp.cpp:89).
- `RunMcp` rejects an oversized completed line at line 130 and also checks `pending.size()>MAX_RPC_BYTES` after its inner loop at line 157. A no-newline sender is therefore bounded to the 4 MiB limit plus at most one 8192-byte read chunk in logical payload, before exit; string capacity/allocator overhead is separate. `.substr` creates a completed-line copy, `pending.erase` may shift the remaining suffix, and JSON parsing/serialization introduces further representations. MCP is optional: the pipe thread starts only in `McpMode(next != 0)`. [Local mcp.cpp:124](/D:/workspace/simple-md/src/mcp.cpp:124), [mcp.cpp:157](/D:/workspace/simple-md/src/mcp.cpp:157), [main.cpp:304](/D:/workspace/simple-md/src/main.cpp:304).

### Inferences

1. **P0 — single-pass normalization and spans.** Add pointer+length / `std::string_view` / `std::wstring_view` conversion overloads to eliminate `bytes.substr(offset)` and preview token substrings. Normalize LF in place for owned strings, or avoid work when there is no CR. Build editor line endings once, rather than normalizing an already normalized string again. Validate Unicode without producing an unused converted output. These are local, comparatively low-risk fixes to the specific call paths above. Preserve invalid UTF-8/surrogate/NUL rejection. [Local document.cpp:12](/D:/workspace/simple-md/src/document.cpp:12), [mcp.cpp:7](/D:/workspace/simple-md/src/mcp.cpp:7).
2. **P0 — streaming fingerprint.** Implement a fixed-size byte-buffer fingerprint function for conflict checks. Decode only when a changed file must actually be loaded. Metadata (size/time/file identity) can skip likely unchanged files for focus notifications, but the final pre-save conflict decision should retain content verification because metadata alone does not prove equality. This removes redundant decoded whole-file allocations without reducing the existing conflict guarantee. [Local main.cpp:240](/D:/workspace/simple-md/src/main.cpp:240), [document.cpp:23](/D:/workspace/simple-md/src/document.cpp:23).
3. **P1 — bounded streaming I/O with RichEdit.** Save with `EM_STREAMOUT` into the existing adjacent temporary-file/flush/atomic-replace transaction, normalizing and encoding bounded chunks and updating the output fingerprint/byte count while writing. Use `EM_STREAMIN` plus a bounded decoder for loading after validating a stable input, or retain one decoded input as a first simpler step. Streaming removes application-side full copies; it does **not** make RichEdit's stored text or layout virtual. Preserve a trailing CR, partial UTF-8 sequence, or high surrogate across chunk boundaries; check `EDITSTREAM.dwError`, cap final encoded bytes, and leave the original file intact on errors. [Microsoft EM_STREAMOUT](https://learn.microsoft.com/en-us/windows/win32/controls/em-streamout), [Microsoft EM_STREAMIN](https://learn.microsoft.com/en-us/windows/win32/controls/em-streamin), [local document.cpp:55](/D:/workspace/simple-md/src/document.cpp:55).
4. **P1 — truly bounded MCP document extraction.** Validate offset/limit before `Load`. Retrieve UTF-16 ranges/chunks from the control, count code points and normalize line breaks incrementally, and retain only the requested page. Cache total code-point count against document revision or return it after a bounded-memory scan. For a clean unloaded file, a disk streaming path can serve a page without creating an editor if it preserves revision/external-change semantics. The stdio no-newline input already has a bound; the valid remaining transport opportunities are reducing line/DOM/serialized-result copies and retained capacity, not fixing unbounded accumulation. Avoid copying JSON arguments/content (`const` references where lifetime permits), though that alone does not remove JSON DOM/serialization costs. [Local main.cpp:321](/D:/workspace/simple-md/src/main.cpp:321), [mcp.cpp:124](/D:/workspace/simple-md/src/mcp.cpp:124), [mcp.cpp:157](/D:/workspace/simple-md/src/mcp.cpp:157).
5. For `N` UTF-16 code units, one extra full text string is about `2N` payload bytes on Windows, excluding capacity/allocator overhead. Several of the above copies overlap, but their exact peaks differ by stage and encoding; adding every temporary from all stages would overstate the real peak. Report measured peak private commit/resident and settled working set separately. [Local main.cpp:38](/D:/workspace/simple-md/src/main.cpp:38), [document.cpp:24](/D:/workspace/simple-md/src/document.cpp:24).

### Gaps

- RichEdit's internal text/layout/undo allocation sizes are not observable from these source files. Copy elimination cannot be assigned an exact MiB saving without tracing or before/after measurements.
- Bounded Unicode conversion must be validated with Vietnamese composed/decomposed text, combining marks, emoji/surrogates, CR/LF/CRLF split across boundaries, invalid encodings, and failed writes. Existing code intentionally validates strictly; do not weaken that behavior to save memory. [Local mcp.cpp:7](/D:/workspace/simple-md/src/mcp.cpp:7), [document.cpp:24](/D:/workspace/simple-md/src/document.cpp:24).

## 2. Would gap buffers, ropes, piece tables, file mapping, or tighter caches meet the RAM target?

### Takeaway

A new document structure only saves the existing RichEdit allocation if it replaces RichEdit's ownership of the whole document. A second gap buffer/rope/piece tree synchronized with RichEdit would add memory; a true paged editor is a substantially larger rendering, input, Unicode, selection, and undo project.

### Cited Findings

- VS Code's original piece-tree design keeps immutable original buffers plus a change buffer, with tree pieces referencing ranges; line starts belong to buffers rather than being copied per piece. The author explicitly warns that performance depends on language, environment, and client API. Repeated edits increase node count; line lookup trades array indexing for tree traversal. These results concern a JavaScript text model, not Windows process working-set minima. [Original Microsoft article](https://code.visualstudio.com/blogs/2018/03/23/text-buffer-reimplementation).
- Current VS Code source uses compact 16/32-bit line-start arrays and snapshot piece lists; comments explicitly require immutable pieces and coordination of normalization for actual concurrent snapshot reading. [Microsoft pieceTreeBase.ts](https://raw.githubusercontent.com/microsoft/vscode/main/src/vs/editor/common/model/pieceTreeTextBuffer/pieceTreeBase.ts).
- The original rope paper represents strings as trees with flat string leaves and shared subtrees, supporting sharing rather than repeatedly copying concatenation arguments. It discusses lazy file-backed strings and the need for storage management for shared structures. [Boehm, Atkinson, Plass, 1995](https://www.cs.tufts.edu/comp/150FP/archive/hans-boehm/ropes.pdf).
- Scintilla's official direct-access API describes a gap, movement when a requested range crosses it, and temporary read-only pointers invalidated by editing. Its document can disable style storage; its loader accepts chunks off the UI thread. Layout cache choices include caret, visible-page, and whole-document. [Scintilla official API](https://www.scintilla.org/ScintillaDoc.html#SCI_GETRANGEPOINTER).
- Scintilla's component design separates text/undo/line metadata in `CellBuffer`, document semantics in `Document`, and display/input in `Editor`; undo records text insertion/deletion actions, with styling omitted. [Scintilla official design](https://www.scintilla.org/Design.html).
- Microsoft file mapping permits partial views and unmapping/remapping to access another portion. It is a virtual-address-space association, not a promise that touched file contents avoid physical memory. [Microsoft file mapping](https://learn.microsoft.com/en-us/windows/win32/memory/file-mapping).
- `VirtualAlloc(MEM_RESERVE)` reserves address space without physical/page-file storage; commit and first access are separate. `VirtualFree(MEM_DECOMMIT)` returns pages to reserved state; memory contents are no longer retained there. [Microsoft VirtualAlloc](https://learn.microsoft.com/en-us/windows/win32/api/memoryapi/nf-memoryapi-virtualalloc), [Microsoft VirtualFree](https://learn.microsoft.com/en-us/windows/win32/api/memoryapi/nf-memoryapi-virtualfree).
- The process working set comprises resident pageable pages. Referencing nonresident pages faults them back in; mapping pages are included when resident. Explicit working-set trimming changes residency rather than deleting the document's ownership/allocation. [Microsoft working set](https://learn.microsoft.com/en-us/windows/win32/memory/working-set).
- Existing `TrimEditors` counts clean controls and estimated UTF-16 text payload, keeping up to three clean controls / 8 MiB payload. It excludes dirty documents and preserves current/in-flight MCP documents; cached-control overhead, layout, undo and preview are outside this payload budget. Folder opening already keeps only path/title metadata until selection. [Local main.cpp:182](/D:/workspace/simple-md/src/main.cpp:182), [main.cpp:215](/D:/workspace/simple-md/src/main.cpp:215).
- `EM_SETUNDOLIMIT` bounds the **number of actions**, not their byte size; zero disables undo. Current limits are four for initially large documents and 32 for small; ordinary typing growth does not dynamically lower the limit. [Microsoft EM_SETUNDOLIMIT](https://learn.microsoft.com/en-us/windows/win32/controls/em-setundolimit), [local main.cpp:169](/D:/workspace/simple-md/src/main.cpp:169), [main.cpp:269](/D:/workspace/simple-md/src/main.cpp:269).

### Inferences

- **P1 — strict-memory cache mode:** keep only the selected clean editor, or a much smaller measured byte budget; evict other clean controls when selection changes and after save. Preserve path, encoding, fingerprint, revision, selection and scroll position. This lowers multiple-open-file steady memory, at the price of decode/reflow latency when revisiting tabs and lost native undo for evicted documents. Caching 2–3MB of *total* process working set cannot follow from an 8 MiB clean-source budget, even before dirty documents. [Local main.cpp:182](/D:/workspace/simple-md/src/main.cpp:182).
- **Dirty retention is a deliberate unbounded category.** Multiple unsaved documents cannot all remain in RAM under a hard arbitrary total cap. A future disk-backed recovery snapshot + edit journal could dehydrate inactive dirty documents, keeping unsaved status and original save semantics. Never evict dirty contents to the original file automatically. This adds temporary-file lifecycle, failure recovery, conflict handling and an undo-persistence policy; it is not a small LRU tweak. [Local main.cpp:22](/D:/workspace/simple-md/src/main.cpp:22), [main.cpp:182](/D:/workspace/simple-md/src/main.cpp:182), [main.cpp:246](/D:/workspace/simple-md/src/main.cpp:246).
- **Undo byte budget:** four giant replace/paste/delete actions can still retain large content. Adapt native action limit after ordinary document growth, but a strict byte limit requires ownership of history (or a documented policy to clear history after certain huge edits). Clearing history is a user-visible capability loss. A custom journal should record deltas, coalesce adjacent typing, cap retained bytes, and release unreferenced backing chunks when pruning. [Microsoft EM_SETUNDOLIMIT](https://learn.microsoft.com/en-us/windows/win32/controls/em-setundolimit), [local main.cpp:333](/D:/workspace/simple-md/src/main.cpp:333).
- **Gap buffer:** likely the simplest contiguous custom buffer for mostly local typing, but moving the gap for distant edits and spare-capacity retention remain costs. Good locality is not evidence of lower *total* RAM than native RichEdit; it still needs a view/input stack. **Piece table/tree:** original mapped bytes plus appended edit chunks can avoid copying unchanged ranges and support persistent snapshots; deleted text/change chunks must be compacted after undo/snapshot references expire. **Rope:** appropriate if large immutable snapshot/concatenation operations dominate, but tree-node/refcount overhead and flattening into full strings can cancel benefits. Prefer the smallest model that matches measured access patterns. [Microsoft article](https://code.visualstudio.com/blogs/2018/03/23/text-buffer-reimplementation), [rope paper](https://www.cs.tufts.edu/comp/150FP/archive/hans-boehm/ropes.pdf), [Scintilla direct access](https://www.scintilla.org/ScintillaDoc.html#SCI_GETRANGEPOINTER).
- **Mapping versus streaming:** with today's full RichEdit buffer, mapping input only removes the encoded `bytes` allocation; full decode/text remains. Streaming with a small read buffer is simpler for sequential fingerprint/load/save. Mapping becomes most valuable with a custom paged viewer/editor reading only visible windows, a sparse line/checkpoint index and bounded decoded/layout caches. Whole-file scans for hash/search/parse still touch every page. An original-file mapping needs a stable-content/replace strategy because external writes or saves can invalidate assumptions. [Microsoft file mapping](https://learn.microsoft.com/en-us/windows/win32/memory/file-mapping), [local document.cpp:24](/D:/workspace/simple-md/src/document.cpp:24).
- **No guaranteed 2–3MB total:** none of these structures removes already-needed Windows image/font/control resident pages. The supplied empty measurement has no loaded document buffer to optimize. Artificially trimming to achieve a screenshot number can immediately refault on the next input/render and contradict the no-lag requirement. [Microsoft working set](https://learn.microsoft.com/en-us/windows/win32/memory/working-set), [local main.cpp:105](/D:/workspace/simple-md/src/main.cpp:105).
- **Scintilla experiment, not guaranteed recommendation:** a small optional prototype using plain UTF-8 documents, no styles, no lexer, bounded page layout cache and one view with document swapping can test loaded-document overhead. It remains a real editor with input/selection APIs, but does not provide a hard total-process cap or automatically disk-page the file. UTF-8 is not universally smaller than UTF-16 for Vietnamese; compare actual corpora and Unicode input behavior. [Scintilla API](https://www.scintilla.org/ScintillaDoc.html#SCI_CREATEDOCUMENT), [local main.cpp:163](/D:/workspace/simple-md/src/main.cpp:163).

### Gaps

- No benchmark supports claiming a rope, piece tree, Scintilla, or mapped custom editor will meet 2–3MB total working set on this Windows installation.
- RichEdit offers no supplied public byte-accounting interface for its undo/layout cache; this source inspection cannot make its payload budget a strict process memory guarantee.
- Any replacement needs measured Vietnamese IME/Telex/VNI interaction, combining-mark caret/delete behavior, surrogate-safe offsets, clipboard, accessibility, selection, search and multi-file save before replacing a mature native text control.

## 3. How should preview work, cancellation, and resource lifetimes change?

### Takeaway

The existing lazy preview and debounce are good starting points, but memory should be bounded by rendered-output bytes as well as source length. Cancel superseded work early and bound completed results; consider visible-block rendering only as a later architecture change.

### Cited Findings

- Source editing has a 300 ms timer. Preview is skipped in Edit mode and replaced by a small notice above 400,000 UTF-16 code units. One worker consumes one replaceable pending source; completed results are posted as heap-owned messages and applied only if document/generation still match. [Local main.cpp:269](/D:/workspace/simple-md/src/main.cpp:269), [main.cpp:282](/D:/workspace/simple-md/src/main.cpp:282), [main.cpp:131](/D:/workspace/simple-md/src/main.cpp:131).
- No callback checks cancellation, and `StopWorker` sets a flag then joins: an in-progress `MarkdownRtf` always runs to completion. Switching to Edit destroys the preview and clears pending input but retains the worker until reset/close. Final document close stops worker, drains completed messages, destroys preview/list and unloads Msftedit. [Local main.cpp:145](/D:/workspace/simple-md/src/main.cpp:145), [main.cpp:146](/D:/workspace/simple-md/src/main.cpp:146), [main.cpp:299](/D:/workspace/simple-md/src/main.cpp:299).
- `MarkdownRtf` builds a complete RTF string. `Escape` decodes each text callback into a temporary UTF-16 string, then returns another temporary encoded RTF string to append; non-ASCII code units become ASCII RTF `\\u` escapes. RichEdit then parses and stores the preview separately from source. [Local markdown.cpp:5](/D:/workspace/simple-md/src/markdown.cpp:5), [markdown.cpp:89](/D:/workspace/simple-md/src/markdown.cpp:89), [main.cpp:293](/D:/workspace/simple-md/src/main.cpp:293).
- MD4C callbacks may return nonzero to abort parsing, and `md_parse` returns that value. MD4C also supports a Windows UTF-16 build when both parser and header are built with `MD4C_USE_UTF16`; the vendored header contains both capabilities. Its public parse interface takes one contiguous input, not a persistent incremental edit state. [MD4C original header](https://raw.githubusercontent.com/mity/md4c/master/src/md4c.h), [local vendored header:33](/D:/workspace/simple-md/vendor/md4c.h:33), [local vendored header:360](/D:/workspace/simple-md/vendor/md4c.h:360).
- Windows exposes a system-wide low-memory notification object that applications can wait/query to scale usage. This is pressure signaling, not per-application budget enforcement. [Microsoft CreateMemoryResourceNotification](https://learn.microsoft.com/en-us/windows/win32/api/memoryapi/nf-memoryapi-creatememoryresourcenotification).

### Inferences

1. **P0 — bound RTF expansion and stale work.** Carry an atomic generation/cancellation token and an output-byte budget into every MD4C callback; abort before an append exceeds budget. Treat cancellation separately from rendering errors, so the current catch-all does not render an error document for canceled work. Check again before posting. Use one replaceable completed-result slot plus a notification message, or otherwise ensure queued completed RTF objects are bounded. Current pending-source coalescing does not bound the message queue's completed results when the UI is busy. [Local main.cpp:131](/D:/workspace/simple-md/src/main.cpp:131), [markdown.cpp:17](/D:/workspace/simple-md/src/markdown.cpp:17), [MD4C header](https://raw.githubusercontent.com/mity/md4c/master/src/md4c.h).
2. **P0 — append escaped spans directly.** Make `EscapeAppend(Renderer&, pointer, length)` append into the final result, decoding without token `std::string`/`std::wstring` copies and checking the output cap. This preserves current parser/control architecture while reducing allocations per token. A UTF-16 MD4C build could avoid the full UTF-16→UTF-8→per-token UTF-16 round trip, but compare its larger ASCII-heavy input snapshot against the existing UTF-8 snapshot before selecting it. [Local markdown.cpp:5](/D:/workspace/simple-md/src/markdown.cpp:5), [main.cpp:288](/D:/workspace/simple-md/src/main.cpp:288), [MD4C header](https://raw.githubusercontent.com/mity/md4c/master/src/md4c.h).
3. **P1 — explicit lifecycle:** on Edit-only mode, cancel in-flight output and discard stale completed output immediately. Worker teardown can save committed resources but must not repeatedly block the UI on an uninterruptible parse; cancellation should precede shutdown. Reuse a worker while preview remains active, and release per-render source/output capacity once no longer useful. Keep the current lazy loading of preview/control/library and MCP. [Local main.cpp:118](/D:/workspace/simple-md/src/main.cpp:118), [main.cpp:145](/D:/workspace/simple-md/src/main.cpp:145), [main.cpp:299](/D:/workspace/simple-md/src/main.cpp:299), [main.cpp:304](/D:/workspace/simple-md/src/main.cpp:304).
4. **P2 — incremental/visible preview:** merely rendering a source substring around the viewport can misparse fences, nested lists, reference definitions and tables. A correct solution needs block boundaries/dependencies, invalidation of following parse context, source-to-render offsets and bounded block-height/layout cache; RichEdit full-stream replacement must also be replaced or updated by block ranges. MD4C's current one-shot API supplies no incremental edit engine. The existing 400k cutoff is a safe explicit cap while this larger work remains unproven. [MD4C header](https://raw.githubusercontent.com/mity/md4c/master/src/md4c.h), [local markdown.cpp:93](/D:/workspace/simple-md/src/markdown.cpp:93), [main.cpp:293](/D:/workspace/simple-md/src/main.cpp:293).
5. **Pressure response:** when signaled, evict inactive clean editors and preview caches; do not discard unsaved buffers. Use this in addition to explicit byte budgets, with hysteresis to avoid repeated evict/reload oscillation. Saving inactive dirty documents sequentially can cap temporary I/O allocations, while persistent unsaved content still needs its own budget/spill policy. [Microsoft memory notification](https://learn.microsoft.com/en-us/windows/win32/api/memoryapi/nf-memoryapi-creatememoryresourcenotification), [local main.cpp:182](/D:/workspace/simple-md/src/main.cpp:182).

### Gaps

- Callback cancellation is cooperative; MD4C may do substantial internal work before its next callback. The API does not guarantee a maximum cancellation latency. Measure pathological markdown and long single-line inputs before promising zero lag. [MD4C header](https://raw.githubusercontent.com/mity/md4c/master/src/md4c.h).
- Exact RTF expansion, preview-control overhead, worker committed stack, allocator retention and remaining private resident memory require measurements. Source character count alone is not an output-memory bound. [Local markdown.cpp:5](/D:/workspace/simple-md/src/markdown.cpp:5), [main.cpp:131](/D:/workspace/simple-md/src/main.cpp:131).
